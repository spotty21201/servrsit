## T-073 Baseline compare and prepare a server (UX-09, UX §12, FR-09, FR-15), `/baselines`
**Files:** `apps/web/src/baselines/` (`BaselineScreen.tsx`, `baselineLogic.ts` + test, `baselines.module.css`); `apps/web/src/api/stubs/baselines.ts` (types, proposed endpoints and API rules in the header; in-memory fixture client); changes to the canonical plan screen (see below); route in `lib/router.ts` and `App.tsx`; a "Compare with a baseline" link in the server detail's Care section (its Baseline row now says the comparison runs on sample data).

**Flow:** Choose reference (role and observation age; an observation older than a day is flagged; text says the reference is evidence, not a clone source) → Select conventions (checkboxes for directories and Ubuntu packages; a visible "Not eligible" list with the reason for `/etc/ssh` host keys, `/home/*` personal files, `/etc/netplan` network settings, database files and third-party packages; save creates a named, versioned baseline naming the source observation, and says saving authorizes nothing) → Compare target (labels exactly **Matches, Missing, Different by design, Conflict, Not checked**; grouped into Needs a decision / Different by design / Not checked / Matches, with a summary sentence; **Mark intentional** only for Missing or Conflict, with an optional reason, scoped to that machine, shown as "This changed the exception record only, not the server", undoable, and appended to a visible history) → Review plan (what a setup would create, install and leave alone, and the exclusion statement: credentials, SSH host keys, application data, databases, personal files, existing contents and network settings are not copied).
- "Left alone" lists conflicts, unchecked items and items marked intentional, each with its reason. Only Missing items are created. Nothing is copied or deleted by comparing. Repeating a completed setup reads "Nothing to create or install" and offers no plan.
- **Open the plan goes to the same Plan review screen as updates** (`/plans/:id`, T-060), extended for setup plans: `PlanView.prepare` (optional, in `api/stubs/care.ts`) adds directories, a "Left alone" list and the baseline name. The title reads "Prepare {server} from {baseline}", the approval label is "Approve setup of {server}", and the exclusion list, impact, verification ("every requested convention is checked on its own") and the not-established list are specific to setup. Fixture plans: `fixture-plan-prepare` (simulated target, ready) and `fixture-plan-prepare-blocked` (real host, `WRITES_DISABLED`). **A setup plan for a real host opens blocked with no approve button**, verified in the browser (0 approve buttons, the fixed "Changes are switched off…" sentence); the review step warns about that before opening.

## T-074 Settings (UX-11, UX §13.2 and §14, FR-19, FR-21, FR-03), `/settings`
**Files:** `apps/web/src/settings/` (`SettingsScreen.tsx`, `settingsLogic.ts` + test, `settings.module.css`); `apps/web/src/api/stubs/settings.ts` (proposed endpoints and API rules in the header; fixture client).
- **Schedules:** health-check interval (5/15/30/60, default 15), daily deeper-check time (default 03:00), time zone (default Asia/Jakarta; full name and abbreviation shown), defaults stated before saving, next health and daily run with the zone and a relative time (none while paused, never a stale time; ≈ when ServrSit's clock is untrusted), **pause as a separate immediate action** from saving, "Checks paused" notice reused from T-070. Next-run maths is DST-aware and tested (Berlin spring-forward case). The statement "No schedule can install updates, restart a service, reboot or clean anything up" is shown. Allow package-list refresh is stated as off and not available.
- **AI and data:** On/Off switch with what turning it off does and does not stop; provider and route shown (fixture text; region shown as "—, not reported yet"); what is collected, what is not, what is sent to the AI (never credentials or file contents), retention (30 days observations and chat, 90 days operation records, labelled proposed), export (link to Activity), deletion (states that self-service arrives with Stage B and that nothing here deletes data now).
- **Server access:** per server: Production label, inspect-only access, key in use ("dedicated ServrSit key" or "owner key", never a path; an owner key gets a recommendation), host-key confirmation time. **Disconnect {name}…** opens an inline confirmation that names the server, says what stops, lists queued work (will be cancelled) and active work (ServrSit cannot stop it and it may keep running), what stays (the server is not deleted or shut down; history stays), and the user's own step on the server. Focus goes to the confirmation heading (not to the destructive button) and returns to the Disconnect button on Cancel. The result is a persistent panel from the contract's `DisconnectResponse`: what was done, what was not (the remote key line is **never** claimed removed; running work that may continue), the steps and the exact `authorized_keys` line with Copy, and a Reconnect link.
